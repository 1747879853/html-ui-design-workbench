# 复杂业务工作台与单据编辑页 UI / 交互重构沉淀指南 (Playbook)

> 本指南提炼自 [`pages/comprehensive-business-edit.html`](../pages/comprehensive-business-edit.html)（货代综合业务工作台 #178 左右同屏重构）的多轮打磨实战经验，旨在作为本项目后续所有复杂表单、双轨工作台、单证附件页重构的**最高优先级设计准则**。

---

## 一、核心设计哲学：寻找「结构质感」与「极简克制」的黄金平衡点

在重构企业级 B2B 复杂单据页时，最容易陷入两个极端：
- **极端 A（过于平庸 / 传统表单堆砌）**：把十几个 `<a-input>` / `<a-select>` 平铺在白底面板上，靠粗暴的分割线切块，视觉沉闷、缺乏业务主次，满屏灰框与普通输入框混杂。
- **极端 B（用力过猛 / 说明文刷屏）**：为了体现业务规则，把开发文档里的校验规则（如 `同公司校验·最多1票`、`限64字`、`4位小数`、`sortNo:90`、`点击行预览·点铅笔改名`）和中英文括号（`船名 (Vessel)`、`应收明细 (Receivables)`）全写到界面上，导致字多、杂乱、廉价。

### 黄金平衡法则（Golden Balance）
1. **用「结构化微组件」提供精致感，而非用「解释性文字」填满屏幕**：
   - 界面质感来自：**浅石板底色 (`#f3f5f8`) 衬托模块化白底子卡 (`#ffffff`)**、**三格高密度只读底账条**、**双层存根票卡**、**2 列内嵌式协同胶囊矩阵**、**登机牌式起目港直选器**、**深色石板同屏原件预览舱**。
   - 文案必须极度克制：字段标签只保留纯中文核心词（如 `所属公司`、`关联主单`、`委托单位`、`船公司`、`船名`、`航次`、`毛重`、`尺码`），**严禁在标签右侧堆砌灰色规则小字**。
2. **消灭「静态装饰图 + 下方输入框」的 100% 信息重复**：
   - **反模式**：上方画一张静态路线图展示 `CNTAO -> USLAX`，紧接着下方又放两个起运港、目的港下拉框；或者上方用 3 个大字展示 `500 件 / 2500 KGS / 15.5 CBM`，下方紧接着又是这 3 个数字输入框。
   - **正确范式**：
     - **融合式控件**：将航线拓扑可视化（大号港口代码 + 船名航次胶囊 + 单向航线箭头 `───▶`）与起运港/目的港 `<a-select>` 融为同一张登机牌组件。
     - **增量计算条**：货量区上方不重复件重尺原值，而是实时计算并展示货代增量指标（`计费重: 15.50 RT`、`[轻泡货 · 按体积计费]`、`泡重比 1:6.2 · 均重 5.0 kg/件`）。

## 二、严守领域真实性：拒绝伪需求与 C 端错位习惯

1. **严禁虚构后端不存在的 AI / OCR / 自动提取联动**：
   - 若真实代码边界中没有「OCR 票面字段提取比对」或「从附件一键提取数据覆盖左栏表单」，**严禁在原型中编造字段比对表或提取按钮**。
   - 附件预览区下方应展示 100% 真实的元数据属性卡（`关联单号`、`附件类型`、`文件大小`、`上传信息`）。
2. **警惕将 C 端交互习惯生搬硬套到 B 端货代/ERP**：
   - **反例 1：「互换港口」按钮**：C 端买机票/火车票高频使用「互换起终点」（因为有往返程），但 B 端货代工作单从建立起就绑定了单向贸易流向（如海运出口），在航线正中间放 `[⇄ 互换港口]` 显得外行且廉价。应使用纯粹的**单向航线箭头 (`───▶`)**。
   - **反例 2：「齐套 17/17」字段计数**：在货代术语中，「齐套」特指通关单证齐套，且综合业务大量表单字段本就是非必填，统计“填满了 17 个输入框”不仅毫无业务意义，还会误导操作员。
3. **按「用户心智模型」收敛控制层级，而非照搬底层接口字段粒度**：
   - **典型案例：附件「客户可见」**：虽然底层接口在每个附件文件条目上都存有 `clientVisible` 布尔值，但**在用户感知侧，只需要知道并控制「按附件类型维度是否对客户可见」**。
   - **设计落地**：将 `客户可见` 勾选框严格限制在**顶部附件类型卡片这一层**，彻底移除文件列表中的单行 Switch 列、上传条中的重复复选框以及右侧预览卡上的单条可见标签。单层控制即可消除 80% 的视觉噪音。

## 三、微观控件精致度规范 (Micro-Craft Standards)

### 1. 严禁「双重边框嵌套 (Box-in-a-Box)」
- **反模式**：外层用一个带边框的灰底 `div` 容器，里面直接塞两个标准的 `<a-button size="small">`（如翻票器 `[ < 上一票 | 1 / 5 | 下一票 > ]`），导致出现内外双层边框、圆角冲突、禁用态整块死灰、与旁侧按钮高度不一致。
- **正确规范（一体化等高分段工具条）**：
  - 顶栏右侧所有工具控件统一严格锁定 **`28px` 高度**、**`6px` 圆角**、**`1px solid #e2e8f0` 细边框** 与微投影 `0 1px 2px rgba(15, 23, 42, 0.03)`。
  - 翻票器采用单层白底胶囊容器（`overflow: hidden`），内部按钮无边框（`background: #ffffff`），中间序号区采用 `#f8fafc` 浅底与 `1px solid #f1f5f9` 细分割线；**禁用态仅置灰文字与图标 (`#cbd5e1`)，严禁将整个按钮背景涂成深灰**。

### 2. 拒绝生硬的 `01 / 02 / 03 / 04` 数字方块贴片
- **反模式**：在非步骤条的常驻表单卡片标题前贴 `[01]`、`[02]`、`[03]` 蓝底数字方块，像 PPT 目录页一样生硬。
- **正确规范**：
  - **面板顶部快速定位栏**：采用 **4 等分凹槽分段控制器（Segmented Control）**（`background: #f1f5f9; padding: 2.5px; border-radius: 6px`），激活项以白底微投影胶囊浮起（`[ 📄 单据归属 | 👥 客户协同 | 🧭 航程船期 | 📦 货量计费 ]`）。
  - **子卡片标题前缀**：采用 **20×20px 4 色柔和语义图标徽章**（蓝色单据、靛紫团队、青绿罗盘、琥珀货箱），自然区分模块属性。

### 3. 复杂单证/附件管理页签黄金布局
- **反模式**：3 列 × 2 行的 `180px` 固定高度小卡片网格（文件多时每个小框各自出现局促滚动条，文件少时大片留白，放上规则说明又拥挤不堪）。
- **正确规范（上导航 + 左列表 + 右同屏预览驾驶舱）**：
  1. **顶部 6 栏分类导航卡**：展示 `全部附件`、各业务分类卡片（带文件计数与分类级 `客户可见` 勾选框，保留 `0` 文件空分类补交入口）及尾部虚线 `+ 添加其他类型`。
  2. **左侧上传条 + 高密度列表 (58% 宽)**：紧凑拖拽/粘贴上传条（含目标分类下拉）+ 高密度文件列表（支持点击行切换右侧预览、行内铅笔改名 `✏️` 锁扩展名、预览/下载/移除）。
  3. **右侧深色石板同屏预览舱 (42% 宽)**：上方直接渲染提单/报关单/发票纸张预览（非内嵌格式引导下载），下方展示紧凑的 `文件属性` 底账卡。

## 四、每次重构交付前的强制自检清单 (Mandatory Pre-Delivery Checklist)

在向用户展示任何 UI 重构结果前，必须通过 Playwright 在 `1920×1080` 视口下真实渲染截图，并用 `read_file` 肉眼逐项核对：

- [ ] **控制台零报错**：Playwright `Console errors count: 0`。
- [ ] **文案去噪检查**：是否删干净了字段旁多余的灰字解释、开发字段名 (`sortNo`)、中英文重复括号 (`(Carrier)`) 和表头操作教学文字？
- [ ] **领域真实性检查**：是否混入了真实代码不存在的 OCR 提取/AI 评分？是否出现了「互换港口」、「齐套 17/17」等不符合 B 端货代习惯的伪组件？
- [ ] **控制层级收敛**：像「客户可见」这类属性是否已收敛到「分类/类型」一层，而非在每一行重复渲染开关？
- [ ] **微观对齐与边框**：顶栏按钮组是否严格等高 (`28px`)、无双层嵌套边框？双列表单同行字段是否处于同一水平基线、无标签折行错位？
